# 架构决策记录（ADR）

## ADR-006 · 日报升级为"单卡全深读 + 云文档全文"双载体

**日期**：2026-08-04
**状态**：已采纳
**上下文**：v1 规范每仓库 180–260 字符四段式（定位/亮点/代码/判断）+ 裸分数，用户反馈"看完不知道项目到底是什么"——载体上限压缩掉了分析深度，分析师维度的分数对读者无信息量，10 个平均用力无人突出。经真实批次（2026-08-03）对比"索引卡+文档"与"单卡深化"两种成品后，用户拍板选后者，并要求取消速览分层、10 个全部完整深读。
**决策**：卡片改为 10 个条目全深读段式（是什么(场景)/为什么火/比同类/关联/风险/建议，每条 250–500 字符），并每日新建一篇飞书云文档承载五段完整版分析，卡片嵌文档链接与底部按钮。禁止裸分数，判断一律翻译为业务语言；业务关联按五类口径逐项判断，命中才写。
**其他考虑过的方案**：索引卡+云文档（方案 A，信息密度分散在两处，用户对比后弃用）；仅替换四段维度不加文档（深度仍受卡片长度约束）。
**影响**：云文档创建当前经由本地 `lark-cli docs +create`（feishu-toolkit 尚无建文档命令，缺口已记入其反馈池）；Codex 自动化提示词与 `feishu-card-spec.md` 同步更新；任务汇报字段新增云文档 url；卡片体积约 5KB，仍远低于 Card 2.0 上限。

## ADR-005 · 每日推荐固定目标 10 个并永久去重

**日期**：2026-07-15
**状态**：已采纳
**上下文**：日报若每天重复展示榜首项目，信息增量很低；若简单从历史总榜继续向后翻，又会逐日引入已经不热门的项目。
**决策**：本地 Codex 每日 08:00 是唯一调度入口，先触发云端采集，再请求当日推荐批次。推荐固定目标 10 个，只从最近一轮采集且热度不低于 20 的候选中选择；仓库一旦进入推荐批次便永久排除，同一自然日重复请求返回同一批。新候选不足 10 个时返回耗尽状态，不从陈旧历史评分或低热度项目补位。
**其他考虑过的方案**：只在本地文件记录会丢失状态；从历史总榜补足 10 个会持续降低时效性；按 30 天冷却允许重复与“推荐过就不重复”的目标冲突。
**影响**：新增推荐批次和推荐项两张表，以及每日推荐接口；日报只分析这一批，不再输出第 11 名之后的长尾雷达。

## ADR-004 · PostgreSQL 云端常驻与每日固定时刻调度

**日期**：2026-07-15
**状态**：部分被 ADR-005 取代
**上下文**：服务需要部署到 ideaflow-tools，向内部调用方提供稳定 API，并形成每天同一业务时刻的可比快照。
**决策**：存储统一迁移到 PostgreSQL 18.1，时间与 JSON 分别使用 `timestamptz` 和 `jsonb`；除健康检查外，整个 HTTP 路由树使用 `X-API-Token`；自动采集按 IANA 时区和每日 `HH:mm` 计算下一次运行，不在进程启动时立即补跑。
**其他考虑过的方案**：保留 MySQL 会增加云端部署分支；固定 24 小时间隔会随重启漂移；只保护采集接口会暴露趋势证据和接口文档。
**影响**：初始 migration 直接重写，不兼容旧本地 MySQL 数据；生产密钥统一放服务器 `.env`。

## ADR-003 · 风险评分不能自动定性刷星

**日期**：2026-07-15  
**状态**：已采纳  
**决策**：异常风险独立输出；低置信度时禁止进入“疑似异常”分类，高风险只进入人工或离线深查。
